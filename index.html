What I work on

Ingestion that holds up

Third-party lab and device results into a FHIR-shaped store with an auditable trail. Idempotent writes, so a retry is not a duplicate; typed rejections, so a refused record says why rather than vanishing into a log.

Evidence — de-clouding a shelf of IoT devices

Problem

Cheap consumer infrared controllers built on the Tuya BK7231N ship tethered to a vendor cloud: an account, an outbound tunnel that is always up, and a third party in the path of every button press inside the house. The device works until somebody else's service does not.

Action

Reflashed the chip to ESPHome and moved every control path onto an authenticated one. The controller talks to each node over ESPHome's encrypted native API with a per-node key; the unauthenticated per-device web dashboard is gone from the firmware; the build dashboard sits behind an authenticating reverse proxy with automated certificates instead of on a flat network. Nothing accepts an inbound connection from the internet.

Outcome

No vendor account, no cloud dependency, no third party in the path — and a control plane authenticated at the device layer rather than trusted because it happens to be on the LAN.

Two details worth keeping, because they are the kind you only have if you did it. Removing the dashboard from the configuration did not close it: old firmware keeps serving what it was flashed with, so it stayed open until each node was re-flashed. And the on-board temperature sensor self-heats about 20 °C inside a sealed case, so the reading is corrected with a calibration offset against a reference thermometer. Hardware is never the ideal on paper.

Live — the console is the point

Below is a game. The game is the bait; the panel beside it is the work. The browser holds no rules at all — every click is a command sent to a server, decided there, and answered with either a new state or a typed reason for refusal. Every command after the handshake is signed and carries a counter the server will not accept twice. Every number on that panel is measured; none of it is decoration.

It demonstrates real-time state synchronisation, server-side validation, session resumption and replay protection. It does not demonstrate FHIR or PHI handling: it is the same authoritative-state pattern I ship in production APIs, minus the part where it touches anyone's data.

Specified, reviewed and operated by me; the implementation was written with Claude against that specification and the test suite in the public repository.

Nothing leaves your machine until you press start. Press it and this page opens a connection to the game server, which sees your address the way any server you connect to does. It keeps a match id in your browser so you can pick a game back up. No cookies, no analytics, nothing else about you is kept. Scores are ephemeral and reset weekly.

Every command after the handshake is signed with a key the server mints for this connection and hands to this page, and carries a counter the server will not accept twice. You can read that key in devtools — so the envelope protects the session, not against the player. Anti-cheat is the server refusing illegal moves, and nothing else.

The state digest is how you check no tab is showing you a stale board: open the same match in a second tab and both print the same digest. It is not a security control — the server computes it and the client prints it.
